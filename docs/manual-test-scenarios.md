### 시나리오 1: 신규 회원가입 - 첫 프로젝트 생성 - 분석 확인

**시나리오 번호:** TC-001
**시나리오 이름:** 신규 회원가입 후 첫 프로젝트 생성 및 분석 결과 확인

#### 테스트 목적

신규 사용자가 회원가입부터 프로젝트 생성, 분석 결과 확인까지의 전체 핵심 플로우가 정상적으로 동작하는지 검증한다.

#### 사전 조건

- 테스트 서버(http://35.89.105.181)가 정상 가동 중이어야 한다.
- 가입에 사용할 이메일(test-user01@test.com)이 아직 가입되지 않은 상태여야 한다.
- 브라우저 캐시 및 쿠키가 초기화된 상태에서 시작한다.

#### 단계별 테스트 절차

1. 브라우저에서 http://35.89.105.181 에 접속한다.
2. 로그인 페이지에서 **회원가입** 링크 또는 버튼을 클릭한다.
3. 회원가입 폼에 다음 정보를 입력한다:
   - 이메일: `test-user01@test.com`
   - 비밀번호: `TestUser1234!`
   - 비밀번호 확인: `TestUser1234!`
   - 닉네임/이름: `테스트유저01`
   - 역할(해당 시): 크리에이터
4. 회원가입 버튼을 클릭한다.
5. 회원가입 성공 메시지 또는 자동 로그인 여부를 확인한다.
6. (자동 로그인이 아닌 경우) 가입한 이메일과 비밀번호로 로그인한다.
7. 대시보드 페이지가 정상적으로 로드되는지 확인한다.
8. **프로젝트 생성** 버튼을 클릭한다.
9. 프로젝트 생성 폼에 다음 정보를 입력한다:
   - 프로젝트명: `유튜브 요리채널 수익분석`
   - 카테고리: 콘텐츠/크리에이터
   - 판매 가격: 50,000원 (예: 협찬 단가)
   - 예상 월 판매량: 10건
   - 고정비: 500,000원 (장비 감가상각, 편집 소프트웨어 등)
   - 변동비: 20,000원 (식재료, 소품 등)
10. 프로젝트 저장 버튼을 클릭한다.
11. 생성된 프로젝트 상세 페이지로 이동되는지 확인한다.
12. **분석** 탭을 클릭한다.
13. 분석 결과에서 다음 지표를 확인한다:
    - 손익분기점(BEP)
    - 실질 시급
    - 공헌이익률

#### 기대 결과

- 회원가입이 정상적으로 완료되고, 로그인 후 대시보드에 진입할 수 있다.
- 프로젝트가 정상적으로 생성되며, 대시보드에 해당 프로젝트 카드가 표시된다.
- 분석 탭에서 BEP, 실질 시급, 공헌이익률이 숫자로 정상 계산되어 표시된다.
- BEP는 고정비 / (판매가격 - 변동비) = 500,000 / (50,000 - 20,000) = 약 16.7건으로 계산되어야 한다.
- 공헌이익률은 (판매가격 - 변동비) / 판매가격 = 60%로 표시되어야 한다.

#### 확인 포인트 (체크리스트)

- [ ] 회원가입 폼의 유효성 검사가 동작하는가 (빈 필드, 비밀번호 형식 등)
- [ ] 회원가입 성공 후 적절한 피드백 메시지가 표시되는가
- [ ] 로그인 후 대시보드가 빈 상태(프로젝트 없음)로 올바르게 표시되는가
- [ ] 프로젝트 생성 폼의 모든 필드가 정상적으로 입력되는가
- [ ] 프로젝트 저장 시 로딩 인디케이터가 표시되는가
- [ ] 분석 탭에서 BEP 값이 올바르게 계산되어 표시되는가
- [ ] 분석 탭에서 실질 시급이 표시되는가 (타임로그 미입력 시 안내 메시지 확인)
- [ ] 분석 탭에서 공헌이익률이 올바르게 계산되어 표시되는가
- [ ] 페이지 전환 시 깨지는 UI 요소가 없는가

### 시나리오 2: 기존 페르소나 로그인 - 대시보드 확인

**시나리오 번호:** TC-002
**시나리오 이름:** 기존 크리에이터 페르소나 로그인 및 대시보드 정보 확인

#### 테스트 목적

사전 시드된 페르소나 계정으로 로그인하여 대시보드의 프로젝트 카드, 상태 배지, 요약 지표 등이 정상적으로 표시되는지 검증한다.

#### 사전 조건

- 테스트 서버(http://35.89.105.181)가 정상 가동 중이어야 한다.
- `creator01@test.com` 계정이 시드 데이터와 함께 존재해야 한다.
- 해당 계정에 최소 1개 이상의 프로젝트가 시드 데이터로 생성되어 있어야 한다.

#### 단계별 테스트 절차

1. 브라우저에서 http://35.89.105.181 에 접속한다.
2. 로그인 폼에 다음 정보를 입력한다:
   - 이메일: `creator01@test.com`
   - 비밀번호: `Test1234!`
3. 로그인 버튼을 클릭한다.
4. 대시보드 페이지가 로드되는지 확인한다.
5. 대시보드에 표시된 **프로젝트 카드** 목록을 확인한다.
6. 각 프로젝트 카드에 표시된 **상태 배지**(예: 진행중, 완료, 분석중 등)를 확인한다.
7. 대시보드 상단 또는 사이드바의 **요약 지표**(총 프로젝트 수, 평균 수익률 등)를 확인한다.
8. 프로젝트 카드 중 하나를 클릭하여 상세 페이지로 이동하는지 확인한다.
9. 뒤로 가기 버튼을 눌러 대시보드로 정상 복귀하는지 확인한다.

#### 기대 결과

- 로그인이 즉시 성공하며 대시보드로 리다이렉트된다.
- 대시보드에 시드 데이터로 생성된 프로젝트 카드가 1개 이상 표시된다.
- 각 프로젝트 카드에 프로젝트명, 상태 배지, 핵심 지표 요약이 표시된다.
- 요약 지표 영역에 총 프로젝트 수 등의 정보가 올바르게 표시된다.
- 프로젝트 카드 클릭 시 해당 프로젝트 상세 페이지로 정상 이동한다.

#### 확인 포인트 (체크리스트)

- [ ] 로그인 시 지연 없이 대시보드로 이동하는가
- [ ] 대시보드에 프로젝트 카드가 최소 1개 이상 표시되는가
- [ ] 프로젝트 카드에 프로젝트명이 올바르게 표시되는가
- [ ] 프로젝트 카드에 상태 배지가 올바른 색상과 텍스트로 표시되는가
- [ ] 요약 지표(총 프로젝트 수, 평균 수익률 등)가 숫자로 표시되는가
- [ ] 요약 지표의 수치가 실제 프로젝트 데이터와 일치하는가
- [ ] 프로젝트 카드 클릭 시 올바른 상세 페이지로 이동하는가
- [ ] 대시보드 레이아웃이 깨지지 않고 정상 렌더링되는가
- [ ] 브라우저 뒤로 가기 시 대시보드로 정상 복귀하는가

### 시나리오 3: 프로젝트 수정 - 분석 결과 변화 검증

**시나리오 번호:** TC-003
**시나리오 이름:** 프로젝트 가격 인상 후 BEP 감소 여부 검증

#### 테스트 목적

기존 프로젝트의 판매 가격을 인상했을 때, 분석 결과에서 손익분기점(BEP)이 감소하는지 검증하여 분석 엔진의 실시간 반영 정확도를 확인한다.

#### 사전 조건

- 테스트 서버(http://35.89.105.181)가 정상 가동 중이어야 한다.
- `seller01@test.com` 계정에 최소 1개의 프로젝트가 존재해야 한다.
- 해당 프로젝트에 판매 가격, 고정비, 변동비가 설정되어 있어야 한다.

#### 단계별 테스트 절차

1. 브라우저에서 http://35.89.105.181 에 접속한다.
2. 로그인 폼에 다음 정보를 입력한다:
   - 이메일: `seller01@test.com`
   - 비밀번호: `Test1234!`
3. 로그인 버튼을 클릭하여 대시보드로 진입한다.
4. 대시보드에서 기존 프로젝트 카드를 클릭하여 프로젝트 상세 페이지로 이동한다.
5. **분석** 탭을 클릭하여 현재 BEP 값을 **메모**한다 (예: BEP = 50건).
6. 프로젝트 **설정** 또는 **수정** 버튼을 클릭한다.
7. **판매 가격** 필드를 찾아 기존 값보다 **20% 이상 인상**한다.
   - 예: 기존 30,000원 -> 수정 후 40,000원
8. 저장 버튼을 클릭한다.
9. 저장 성공 메시지가 표시되는지 확인한다.
10. 다시 **분석** 탭을 클릭한다.
11. 변경된 BEP 값을 확인하고, 이전에 메모한 값과 비교한다.
12. 공헌이익률도 함께 변경되었는지 확인한다.

#### 기대 결과

- 프로젝트 수정이 정상적으로 저장된다.
- 판매 가격 인상 후 BEP 값이 이전보다 **감소**한다.
  - BEP = 고정비 / (판매가격 - 변동비) 이므로, 판매가격이 증가하면 분모가 커져 BEP가 감소한다.
- 공헌이익률 = (판매가격 - 변동비) / 판매가격 이므로, 판매가격 인상 시 공헌이익률이 **증가**한다.
- 분석 결과가 즉시(새로고침 없이) 반영된다.

#### 확인 포인트 (체크리스트)

- [ ] 프로젝트 수정 폼에서 기존 값이 올바르게 사전 입력되어 있는가
- [ ] 판매 가격 수정 시 유효성 검사가 동작하는가 (음수, 0, 비정상 값 등)
- [ ] 저장 후 성공 메시지 또는 알림이 표시되는가
- [ ] 분석 탭의 BEP 값이 수정 전보다 감소했는가
- [ ] 분석 탭의 공헌이익률이 수정 전보다 증가했는가
- [ ] 분석 결과가 즉시 반영되는가 (별도 새로고침 불필요)
- [ ] 수정 전후의 값 변화가 수학적으로 올바른가
- [ ] 프로젝트 카드의 요약 정보도 함께 업데이트되는가

### 시나리오 4: 비용 항목 추가/삭제 - 분석 반영

**시나리오 번호:** TC-004
**시나리오 이름:** 비용 항목 추가 및 삭제 후 분석 결과 반영 확인

#### 테스트 목적

프로젝트에 새로운 비용 항목을 추가하거나 기존 비용을 삭제했을 때, 분석 탭의 결과(BEP, 공헌이익률 등)가 정확하게 반영되는지 검증한다.

#### 사전 조건

- 테스트 서버(http://35.89.105.181)가 정상 가동 중이어야 한다.
- `dev01@test.com` 계정에 최소 1개의 프로젝트가 존재해야 한다.
- 해당 프로젝트에 기본 비용 항목이 설정되어 있어야 한다.

#### 단계별 테스트 절차

1. 브라우저에서 http://35.89.105.181 에 접속한다.
2. 로그인 폼에 다음 정보를 입력한다:
   - 이메일: `dev01@test.com`
   - 비밀번호: `Test1234!`
3. 로그인 후 대시보드에서 기존 프로젝트를 클릭하여 상세 페이지로 이동한다.
4. **분석** 탭을 클릭하여 현재 BEP, 공헌이익률 값을 **메모**한다.
5. **비용** 탭을 클릭한다.
6. 현재 등록된 비용 항목 목록을 확인하고, 총 비용 합계를 **메모**한다.
7. **비용 추가** 버튼을 클릭한다.
8. 새 비용 항목을 입력한다:
   - 비용명: `AWS 서버 호스팅`
   - 비용 유형: 고정비
   - 금액: 100,000원
   - 주기: 월간
9. 저장 버튼을 클릭한다.
10. 비용 목록에 새 항목이 추가되었는지 확인한다.
11. 총 비용 합계가 100,000원 증가했는지 확인한다.
12. **분석** 탭으로 이동하여 BEP, 공헌이익률 값을 확인한다.
13. BEP가 이전보다 **증가**했는지 확인한다 (고정비 증가 -> BEP 증가).
14. 다시 **비용** 탭으로 이동한다.
15. 방금 추가한 `AWS 서버 호스팅` 항목의 **삭제** 버튼을 클릭한다.
16. 삭제 확인 대화상자에서 **확인**을 클릭한다.
17. 비용 목록에서 해당 항목이 제거되었는지 확인한다.
18. **분석** 탭으로 이동하여 BEP가 원래 값으로 복원되었는지 확인한다.

#### 기대 결과

- 비용 항목 추가 시 비용 목록과 합계가 즉시 업데이트된다.
- 고정비 100,000원 추가 후 BEP가 증가한다.
- 비용 항목 삭제 시 목록에서 제거되고 합계가 감소한다.
- 비용 삭제 후 BEP가 원래 수치로 복원된다.
- 모든 분석 결과가 비용 변경에 실시간으로 반영된다.

#### 확인 포인트 (체크리스트)

- [ ] 비용 탭에서 기존 비용 항목이 올바르게 표시되는가
- [ ] 비용 추가 폼의 모든 필드가 정상적으로 입력되는가
- [ ] 비용 추가 시 유효성 검사가 동작하는가 (음수 금액, 빈 필드 등)
- [ ] 추가된 비용이 목록에 즉시 나타나는가
- [ ] 총 비용 합계가 정확하게 계산되는가
- [ ] 비용 추가 후 분석 탭의 BEP가 증가했는가
- [ ] 비용 삭제 시 확인 대화상자가 표시되는가
- [ ] 삭제 후 비용 목록에서 항목이 제거되었는가
- [ ] 비용 삭제 후 분석 탭의 BEP가 원래 값으로 복원되었는가
- [ ] 비용 유형(고정비/변동비) 구분이 정확하게 동작하는가

### 시나리오 5: 타임로그 기록 - 실질 시급 변화 확인

**시나리오 번호:** TC-005
**시나리오 이름:** 타임로그 추가 후 실질 시급 변화 확인

#### 테스트 목적

프로젝트에 작업 시간(타임로그)을 기록한 후, 분석 탭에서 실질 시급이 정확하게 계산되고 변화하는지 검증한다.

#### 사전 조건

- 테스트 서버(http://35.89.105.181)가 정상 가동 중이어야 한다.
- `creator02@test.com` 계정에 최소 1개의 프로젝트가 존재해야 한다.
- 해당 프로젝트에 매출(수익) 데이터가 설정되어 있어야 한다.

#### 단계별 테스트 절차

1. 브라우저에서 http://35.89.105.181 에 접속한다.
2. 로그인 폼에 다음 정보를 입력한다:
   - 이메일: `creator02@test.com`
   - 비밀번호: `Test1234!`
3. 로그인 후 대시보드에서 프로젝트를 선택하여 상세 페이지로 이동한다.
4. **분석** 탭을 클릭하여 현재 실질 시급 값을 **메모**한다.
   - 타임로그가 없는 경우, "타임로그를 입력해주세요" 등의 안내 메시지가 표시되는지 확인한다.
5. **타임로그** 탭(또는 작업 시간 기록 메뉴)을 클릭한다.
6. **타임로그 추가** 버튼을 클릭한다.
7. 타임로그 정보를 입력한다:
   - 작업일: 오늘 날짜
   - 작업 내용: `영상 촬영 및 편집`
   - 작업 시간: 5시간
8. 저장 버튼을 클릭한다.
9. 타임로그 목록에 새 기록이 추가되었는지 확인한다.
10. 추가로 타임로그를 하나 더 입력한다:
    - 작업일: 오늘 날짜
    - 작업 내용: `섬네일 제작 및 업로드`
    - 작업 시간: 2시간
11. 저장 버튼을 클릭한다.
12. **분석** 탭으로 이동한다.
13. 실질 시급 값을 확인한다.
    - 실질 시급 = (수익 - 비용) / 총 작업시간
14. 총 작업시간이 7시간(5시간 + 2시간)으로 반영되었는지 확인한다.

#### 기대 결과

- 타임로그가 정상적으로 저장되고 목록에 표시된다.
- 분석 탭에서 실질 시급이 계산되어 표시된다.
- 작업 시간이 증가할수록 실질 시급이 감소하는 경향을 보인다.
- 실질 시급 = (총 수익 - 총 비용) / 총 작업시간 공식에 맞게 계산된다.
- 타임로그가 없던 상태에서 추가 시, 실질 시급이 새로 계산되어 표시된다.

#### 확인 포인트 (체크리스트)

- [ ] 타임로그 탭이 정상적으로 로드되는가
- [ ] 타임로그 추가 폼의 모든 필드가 정상 동작하는가
- [ ] 작업 시간 입력 시 유효성 검사가 동작하는가 (음수, 0, 24시간 초과 등)
- [ ] 저장 후 타임로그 목록에 즉시 반영되는가
- [ ] 타임로그 목록에서 작업일, 작업 내용, 작업 시간이 올바르게 표시되는가
- [ ] 분석 탭의 실질 시급 값이 올바르게 계산되었는가
- [ ] 총 작업시간 합계가 정확한가 (5 + 2 = 7시간)
- [ ] 추가 타임로그 입력 시 실질 시급이 재계산되는가
- [ ] 타임로그 미입력 상태에서 적절한 안내 메시지가 표시되는가

### 시나리오 6: 목표 설정 - 진행률 확인

**시나리오 번호:** TC-006
**시나리오 이름:** 프로젝트 목표 매출 및 기한 설정 후 진행률 확인

#### 테스트 목적

프로젝트에 목표 매출과 기한을 설정한 후, 진행률 바와 일일 판매 페이스가 정확하게 계산되고 표시되는지 검증한다.

#### 사전 조건

- 테스트 서버(http://35.89.105.181)가 정상 가동 중이어야 한다.
- `seller02@test.com` 계정에 최소 1개의 프로젝트가 존재해야 한다.
- 해당 프로젝트에 현재까지의 매출 데이터가 일부 존재해야 한다.

#### 단계별 테스트 절차

1. 브라우저에서 http://35.89.105.181 에 접속한다.
2. 로그인 폼에 다음 정보를 입력한다:
   - 이메일: `seller02@test.com`
   - 비밀번호: `Test1234!`
3. 로그인 후 대시보드에서 프로젝트를 선택하여 상세 페이지로 이동한다.
4. **목표** 탭을 클릭한다.
5. 현재 목표가 설정되어 있지 않은 경우, 목표 설정 안내 메시지가 표시되는지 확인한다.
6. **목표 설정** 또는 **목표 수정** 버튼을 클릭한다.
7. 목표 정보를 입력한다:
   - 목표 매출: 5,000,000원
   - 목표 기한: 오늘로부터 30일 후 날짜
   - 목표 판매 수량: 100건 (해당 필드가 있는 경우)
8. 저장 버튼을 클릭한다.
9. 목표 설정 완료 후 다음 항목을 확인한다:
   - **진행률 바**: 현재 매출 / 목표 매출의 백분율이 시각적으로 표시되는가
   - **현재 달성률**: 정확한 퍼센트 값이 표시되는가
   - **일일 판매 페이스**: 남은 기간 동안 하루에 달성해야 하는 매출/판매량이 표시되는가
10. 진행률 바의 퍼센트와 실제 데이터가 일치하는지 수동으로 계산하여 비교한다.
11. 일일 판매 페이스 = (목표 매출 - 현재 매출) / 남은 일수 가 올바르게 계산되었는지 확인한다.

#### 기대 결과

- 목표가 정상적으로 설정되고 저장된다.
- 진행률 바가 현재 매출 대비 목표 매출의 비율에 맞게 표시된다.
- 일일 판매 페이스가 정확하게 계산되어 표시된다.
- 목표 기한까지의 남은 일수가 올바르게 표시된다.
- 진행률이 0% ~ 100% 범위 내에서 올바르게 표현된다.

#### 확인 포인트 (체크리스트)

- [ ] 목표 탭이 정상적으로 로드되는가
- [ ] 목표 미설정 시 적절한 안내 메시지가 표시되는가
- [ ] 목표 매출 입력 시 유효성 검사가 동작하는가 (음수, 0 등)
- [ ] 목표 기한이 과거 날짜인 경우 경고가 표시되는가
- [ ] 저장 후 진행률 바가 즉시 표시되는가
- [ ] 진행률 바의 퍼센트 값이 수학적으로 정확한가
- [ ] 일일 판매 페이스가 정확하게 계산되었는가
- [ ] 남은 일수가 올바르게 표시되는가
- [ ] 목표 100% 달성 시 축하 메시지 또는 완료 표시가 되는가
- [ ] 목표 수정 시 기존 값이 사전 입력되어 있는가

### 시나리오 7: 커뮤니티 게시글 작성 - 댓글 - 삭제

**시나리오 번호:** TC-007
**시나리오 이름:** 커뮤니티 게시글 작성, 타 사용자 댓글, 게시글 삭제 플로우 검증

#### 테스트 목적

커뮤니티 기능의 핵심 플로우인 게시글 작성, 댓글 달기, 게시글 삭제가 정상적으로 동작하며, 권한에 따른 삭제 제어가 올바르게 작동하는지 검증한다.

#### 사전 조건

- 테스트 서버(http://35.89.105.181)가 정상 가동 중이어야 한다.
- `creator03@test.com` 및 `seller01@test.com` 계정이 정상적으로 로그인 가능해야 한다.
- 커뮤니티 기능이 활성화되어 있어야 한다.

#### 단계별 테스트 절차

**[게시글 작성 - creator03@test.com]**

1. 브라우저에서 http://35.89.105.181 에 접속한다.
2. `creator03@test.com` / `Test1234!`로 로그인한다.
3. **커뮤니티** 메뉴를 클릭한다.
4. 커뮤니티 게시판이 정상적으로 로드되는지 확인한다.
5. **글쓰기** 버튼을 클릭한다.
6. 게시글을 작성한다:
   - 제목: `[테스트] 유튜브 수익 분석 팁 공유합니다`
   - 본문: `안녕하세요. 유튜브 크리에이터로 활동 중인데, 수익 분석 시 꿀팁을 공유합니다. 고정비와 변동비를 꼼꼼히 구분하는 것이 핵심입니다.`
   - 카테고리/태그: (해당 필드가 있는 경우 선택)
7. **게시** 버튼을 클릭한다.
8. 게시글이 정상적으로 등록되었는지 확인한다.
9. 게시글 상세 페이지에서 제목, 본문, 작성자가 올바르게 표시되는지 확인한다.
10. 게시글의 URL(또는 게시글 ID)을 **메모**한다.
11. 로그아웃한다.

**[댓글 작성 - seller01@test.com]**

12. `seller01@test.com` / `Test1234!`로 로그인한다.
13. **커뮤니티** 메뉴로 이동한다.
14. 목록에서 `[테스트] 유튜브 수익 분석 팁 공유합니다` 게시글을 찾아 클릭한다.
15. 댓글 입력란에 다음 내용을 입력한다:
    - `좋은 정보 감사합니다! 셀러 입장에서도 고정비/변동비 구분이 정말 중요하더라고요.`
16. **댓글 등록** 버튼을 클릭한다.
17. 댓글이 게시글 하단에 정상적으로 표시되는지 확인한다.
18. 댓글 작성자가 `seller01`로 표시되는지 확인한다.
19. 로그아웃한다.

**[게시글 삭제 - creator03@test.com]**

20. `creator03@test.com` / `Test1234!`로 다시 로그인한다.
21. **커뮤니티**에서 본인이 작성한 게시글로 이동한다.
22. 댓글이 정상적으로 표시되는지 확인한다.
23. 게시글 **삭제** 버튼을 클릭한다.
24. 삭제 확인 대화상자에서 **확인**을 클릭한다.
25. 게시글이 삭제되고, 커뮤니티 목록에서 해당 게시글이 사라졌는지 확인한다.

#### 기대 결과

- 게시글이 정상적으로 작성되고 목록 및 상세 페이지에 표시된다.
- 다른 사용자가 해당 게시글에 댓글을 달 수 있다.
- 게시글 작성자가 본인의 글을 삭제할 수 있다.
- 삭제된 게시글은 커뮤니티 목록에서 더 이상 표시되지 않는다.
- 삭제된 게시글 URL에 직접 접근 시 적절한 에러 메시지가 표시된다.

#### 확인 포인트 (체크리스트)

### 시나리오 10: 보안 테스트 - 타인 프로젝트 접근 차단

**시나리오 번호:** TC-010
**시나리오 이름:** 타 사용자 프로젝트 URL 직접 접근 시 접근 차단 검증

#### 테스트 목적

인증된 사용자가 다른 사용자의 프로젝트에 URL 직접 입력 방식으로 접근을 시도했을 때, 서버 측에서 올바르게 접근을 차단(403 Forbidden 또는 리다이렉트)하는지 검증하여 데이터 격리 보안을 확인한다.

#### 사전 조건

- 테스트 서버(http://35.89.105.181)가 정상 가동 중이어야 한다.
- `creator01@test.com` 계정에 최소 1개의 프로젝트가 존재해야 한다.
- `seller01@test.com` 계정이 정상적으로 로그인 가능해야 한다.
- 두 계정이 서로 다른 사용자임이 확인된 상태여야 한다.

#### 단계별 테스트 절차

**[creator01의 프로젝트 ID 확인]**

1. 브라우저에서 http://35.89.105.181 에 접속한다.
2. 로그인 폼에 다음 정보를 입력한다:
   - 이메일: `creator01@test.com`
   - 비밀번호: `Test1234!`
3. 로그인 후 대시보드에서 프로젝트를 클릭하여 상세 페이지로 이동한다.
4. 브라우저 주소창의 URL을 확인하고 **프로젝트 ID**를 메모한다.
   - 예: `http://35.89.105.181/projects/abc123` 에서 `abc123`이 프로젝트 ID
5. 해당 프로젝트의 **전체 URL**을 복사해둔다.
6. 프로젝트 상세 페이지에서 프로젝트 데이터(프로젝트명, 매출 등)를 **메모**한다 (나중에 비교용).
7. 로그아웃한다.

**[seller01로 타인 프로젝트 접근 시도]**

8. `seller01@test.com` / `Test1234!`로 로그인한다.
9. 로그인 성공 후 대시보드가 표시되는지 확인한다.
10. 브라우저 주소창에 5번에서 복사한 **creator01의 프로젝트 URL**을 직접 입력한다.
11. Enter 키를 눌러 해당 URL로 이동을 시도한다.
12. 서버의 응답을 확인한다:
    - **403 Forbidden** 에러 페이지가 표시되는가?
    - 또는 **대시보드로 리다이렉트**되는가?
    - 또는 **"접근 권한이 없습니다"** 등의 에러 메시지가 표시되는가?
13. creator01의 프로젝트 데이터(프로젝트명, 매출 등)가 **절대 노출되지 않는지** 확인한다.

**[비로그인 상태에서 접근 시도]**

14. 로그아웃한다.
15. 로그인하지 않은 상태에서 브라우저 주소창에 **creator01의 프로젝트 URL**을 직접 입력한다.
16. Enter 키를 눌러 해당 URL로 이동을 시도한다.
17. 서버의 응답을 확인한다:
    - **로그인 페이지로 리다이렉트**되는가?
    - 또는 **401 Unauthorized** 에러가 표시되는가?

**[API 직접 호출 시도 (선택)]**

18. 브라우저 개발자 도구(F12)를 연다.
19. Console 탭에서 seller01의 인증 토큰을 사용하여 creator01의 프로젝트 API를 직접 호출해본다:
    ```
    fetch('/api/projects/abc123', { headers: { 'Authorization': 'Bearer <seller01의 토큰>' } })
    ```
20. API 응답 코드가 403인지 확인한다.

#### 기대 결과

- seller01 계정으로 creator01의 프로젝트에 접근 시도 시, **접근이 차단**된다.
- 403 Forbidden 응답 또는 대시보드/에러 페이지로의 리다이렉트가 발생한다.
- creator01의 프로젝트 데이터(프로젝트명, 매출, 비용 등)가 seller01에게 **일절 노출되지 않는다**.
- 비로그인 상태에서의 접근 시도 시, 로그인 페이지로 리다이렉트되거나 401 에러가 반환된다.
- API 직접 호출 시에도 동일하게 접근이 차단된다.

#### 확인 포인트 (체크리스트)

- [ ] seller01 로그인 상태에서 creator01의 프로젝트 URL 접근 시 접근이 차단되는가
- [ ] 403 Forbidden 또는 적절한 에러 응답이 반환되는가
- [ ] 에러 페이지에 creator01의 프로젝트 데이터가 노출되지 않는가
- [ ] 대시보드로 리다이렉트되는 경우, seller01 자신의 대시보드로 이동하는가
- [ ] 비로그인 상태에서 프로젝트 URL 접근 시 로그인 페이지로 리다이렉트되는가
- [ ] API 직접 호출 시에도 접근이 차단되는가 (403 응답)
- [ ] 프로젝트 ID를 순차적으로 변경하며 접근 시도해도 차단되는가 (IDOR 방지)
- [ ] 에러 메시지에 서버 내부 정보(스택 트레이스 등)가 노출되지 않는가
- [ ] 접근 차단 로그가 서버 측에 기록되는가 (서버 로그 확인 필요)
- [ ] 다른 사용자 조합(dev01 -> seller01의 프로젝트 등)에서도 동일하게 차단되는가

## 부록: 테스트 수행 시 유의사항

### 테스트 환경 초기화

- 각 시나리오 수행 전 브라우저 캐시 및 쿠키를 초기화하는 것을 권장합니다.
- 시크릿 모드(Chrome) 또는 프라이빗 모드(Firefox)를 활용하면 계정 전환 시 편리합니다.
- 시나리오 7(커뮤니티)의 경우, 두 개의 브라우저 또는 시크릿 모드를 동시에 사용하면 계정 전환이 용이합니다.

### 테스트 결과 기록 방법

각 시나리오 수행 시 다음 정보를 함께 기록해 주십시오:

| 항목 | 내용 |
|------|------|
| 테스트 수행자 | (이름) |
| 테스트 수행일 | (날짜) |
| 브라우저/버전 | (예: Chrome 120.0) |
| 시나리오 번호 | (예: TC-001) |
| 결과 | Pass / Fail / Blocked |
| 발견된 이슈 | (상세 설명) |
| 스크린샷 | (첨부) |

### 알려진 제한사항

- 테스트 서버의 데이터는 주기적으로 초기화될 수 있습니다.
- AI 상담 기능(시나리오 8)은 외부 AI 서비스 상태에 따라 응답 시간이 달라질 수 있습니다.
- 시나리오 1(신규 회원가입)의 가상 계정은 이미 가입된 상태일 수 있으므로, 테스트 전 확인이 필요합니다.
